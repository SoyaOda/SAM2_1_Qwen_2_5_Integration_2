# LISA改: 動的解像度対応の詳細設計プラン

本設計では、Qwen2.5-VLモデルの**Naive Dynamic Resolution**機能を最大限に活用し、SAM2.1のマスクデコーダへ高精細な視覚情報を渡せるようにモデルとデータ処理パイプラインを修正します。将来的なFoodLMM改での料理・食材量推定精度を高めるため、画像の解像度を動的に扱い、**元の画像情報を極力失わず**にモデルへ入力する方針です。また、Qwen2.5-VLが採用する\*\*Multimodal ROPE (M-RoPE)\*\*により、可変サイズの画像でも空間位置を適切にエンコードできるため、非正方形画像や極端なアスペクト比にも対応可能な設計とします。以下に、具体的な修正項目をセクションごとにまとめます。

## データ前処理: 動的解像度リサイズとパディング

* **アスペクト比維持のリサイズ**: 画像は**長辺を基準**にリサイズし、長辺のピクセル数が所定の範囲に収まるよう調整します（短辺はアスペクト比維持）。具体的には、長辺を **最小336px**（約24パッチ相当）以上、**最大2688px**（約192パッチ相当）以下にクランプします。これにより、極端に小さい画像は拡大され、小さい物体や文字も認識しやすくなります。一方で巨大な画像はトークン数上限内に収めるために縮小されます。

* **実装方法**: 上記リサイズポリシーは、Qwen公式のベストプラクティスに従います。例えばHuggingFace版AutoProcessorでは `min_pixels`（最小画素数）と`max_pixels`（最大画素数）で指定可能です。以下のように設定することで、画像を自動的に所定の範囲にリサイズできます。

  ```python
  min_pixels = 336 * 336  # 336px × 336px 相当の画素数（約24×24パッチ）
  max_pixels = 2688 * 2688  # 2688px × 2688px 相当の画素数（約192×192パッチ）
  processor = AutoProcessor.from_pretrained("Qwen/Qwen2.5-VL-7B", 
                                           min_pixels=min_pixels, 
                                           max_pixels=max_pixels)
  ```



  上記設定により、各画像は**元の解像度に基づき**自動リサイズされ、指定範囲（トークン数に換算して約144～9216個）内に収まります。特に `min_pixels` により小さすぎる画像は拡大され、OCRや小物体検出の性能向上が報告されています。

* **パッチサイズ境界へのパディング**: リサイズ後の画像は、それぞれ**パッチサイズ14の倍数**（必要なら28の倍数）となるようにゼロパディングします。例えば、リサイズ結果が340×500pxの場合、14で割り切れる最近傍サイズの**350×504px**までゼロ埋めします。これにより、画像をViTに分割した際に縦横それぞれ整数個（H×W個）のパッチに整列できるようにします。パディング後のパッチ数(H\_patches, W\_patches)は`image_grid_thw`（テンポラル次元T=1、高さH、幅W）として保持し、後続処理に利用します。

* **Qwen Processorの利用**: 可能であれば上記処理はAutoProcessor経由で一括処理します。`HybridDataset.__getitem__`で`self.qwen_processor.apply_chat_template`を呼ぶ際に、Processorに設定した`min_pixels`/`max_pixels`が効くため、個別の`preprocess_qwen_image`実装を簡略化できます。Processor出力の`image_grid_thw`を取得し、各サンプルごとのパッチグリッドサイズ(高さH\_patches, 幅W\_patches)を記録します。

## バッチングとコレーター: 可変解像度のパッチ統合

* **バッチ内の解像度ばらつき対応**: 一つのバッチに異なる画像サイズ（パッチ数）のデータが混在する場合、**各サンプルの視覚トークン列をパディング**して揃えます。`MultiModalDataCollator`を修正し、各サンプルの`image_grid_thw`から**最大のH\_patchesとW\_patches**を算出します。その最大サイズに合わせて、他のサンプルの`pixel_values`（パッチEmbedding列）を**ゼロパッチ**で埋め、テンソル形状を統一します。これにより、異なる解像度の画像でも同一テンソルにまとめてモデルに入力できます（HuggingFaceの`padding=True`と同様の動作）。

* **視覚トークン数の管理**: パディング後の**総パッチ数 = H\_grid\_max × W\_grid\_max**が算出されます。現行実装では、この総パッチ数を**4の倍数**に調整しています。これはQwenの**4:1パッチ圧縮**（後述）の都合上、視覚トークン数が4で割り切れる必要があるためです。調整後の最大パッチ数 (`max_patches`)を用いて `(batch_size, max_patches, D_v)` のバッチテンソルを構築し、各サンプルのパッチEmbedding列を先頭から詰めて配置、残りをパディングします。対応する**attention mask**も拡張し、実パッチに1、パディング部分に0を設定します。こうすることで、LLM側でパディングトークンを無視し、\*\*<|vision\_end|>\*\*トークン以降の視覚情報が実質無効化されるようにします。

* **バッチサイズと解像度のトレードオフ**: 基本的に、Qwen2.5-VLは同一シーケンス内に複数画像・動画が混在するケースでも動作可能であり、公式実装でもバッチ内で様々なメディアを混ぜて処理しています。そのため、本プロジェクトでも**バッチ内で解像度統一の制約は設けず**、必要に応じてパディングで吸収する方針とします。ただし、極端に高解像度の画像と低解像度の画像を同一バッチに入れるとメモリ非効率になるため、学習時に**類似サイズの画像をまとめるバッチ編成**も検討します（例えばDataLoaderでサイズ順にソートするなど）。これは実装上オプションですが、大規模学習での効率を上げるテクニックとして念頭に置いておきます。

## モデル: ViT視覚エンコーダとアダプタの改修

* **ViTへの動的グリッド適用**: Qwen2.5-VLのViTエンコーダは動的解像度を前提としており、Absolute PEを廃してRoPE-2Dで位置エンコードしています。`LISAModel.extract_vision_features`内部で、これまで固定値だった`image_grid_thw`引数に対し、**各バッチの実画像グリッドサイズ**を与えるよう修正します。具体的には、前処理で取得した各サンプルの`image_grid_thw`（形状\[B,3]でT=1, H\_patches, W\_patches）テンソルをViTに渡します。これによりViT内部で**その画像固有のパッチ数**を認識し、正しい2次元位置埋め込みで特徴抽出が行われます（デフォルトの仮想24×24グリッドを撤廃）。フック（`capture_features`）によって取得する**merger直前の特徴**（1280次元×N\_patches）も、N\_patchesが可変長（例: 576や1024等）となることを許容します。なお、QwenのDynamic Resolution実装では**ViT出力後に2×2パッチを1トークンに圧縮するMLP**（merger）が存在しますが、我々は既存実装通り**merger前**の高精細特徴を取得し、下流のSAMに渡します。このフローにより、LLMには圧縮トークンを渡しつつ、SAM用には**元解像度に近い詳細な視覚情報**を保持できます。

* **ImageFeatureAdapterの非正方形対応**: 抽出したViT特徴（サイズ: B×N\_patches×1280）をSAM用にマップする`ImageFeatureAdapter`を修正します。現在は`H = W = sqrt(N)`で空間次元を算出していますが、動的解像度では**HとWが異なる場合**もあります。そこで、アダプタの`forward`に**元のグリッドサイズ(H, W)情報**を渡すよう変更し、reshape処理を明示的に行います。実装上は、例えば`vision_features`にサイズ情報を付与するか、あるいはAdapterを`ImageFeatureAdapter(H, W)`のようにインスタンス化/呼び出しし、`features = features.reshape(B, H, W, 256).permute(0,3,1,2)`で\[B,256,H,W]テンソルに変換します。これにより、どのような縦横比の画像でも**対応する正しい特徴マップ**（256チャネル）が得られます。なお、Qwen2.5-VLは2次元RoPEにより矩形画像の位置も正確にエンコードできるため、この変換で情報が欠落することはありません。

* **高解像度特徴生成 (HighResFeatureGenerator)**: 既存のアップサンプリングモジュールは、入力の空間サイズに依存して動作します。例えば元のViT特徴が\[24×24]ならupsample後は\[48×48]と\[96×96]を出力していました。動的解像度では、入力特徴が\[B,256,H,W]（H,Wは可変）となるため、**2倍・4倍**のアップサンプルにより`feat_s1` (stride-8相当)は\[2H×2W]、`feat_s0` (stride-4相当)は\[4H×4W]となります。これら計算は畳み込み層や補間で実装されており、H,Wが変わっても正しく処理されます。例えば**448px→32×32パッチ**の場合はfeat\_s0が128×128近辺、**2688px→192×192パッチ**ならfeat\_s0は768×768相当の巨大なマップになりますが、演算自体は問題なく機能します。**注意点**として、大きな特徴マップはメモリを圧迫するため、入力解像度上限を2688pxに設定しています（これ以上はSAMの高解像度特徴も過大になり計算量的に現実的でないため）。

* **SAMへの統合**: Mask Decoderへの入力パラメータ生成を動的サイズ対応します。`image_embeddings=image_features_sam`には上記Adapter出力（B,256,H,W）をそのまま渡し、`high_res_features=[feat_s0, feat_s1]`も変更ありません。**重要なのは位置エンコーディング** `image_pe` です。現状実装では固定サイズのSAM用`image_pe`を使い回していないか確認し、**画像毎のH×Wに対応する位置埋め込み**を生成する必要があります。方法としては、SAM2.1のImage Encoderで使われているPositional Embedding生成関数を流用し、(H,W)サイズに合わせた2次元Position Embedding（256ch）を計算します。仮に学習済みの絶対位置エンベッディング（1024入力用）を持っている場合でも、例えば双線形補間でH×Wサイズにリサンプルするか、RoPEなど規則的エンコーディングで代替します。動的解像度に適応するためには、**プログラムで位置埋め込みを構築可能**にしておくことが望ましいです。これにより、Mask Decoderはどの解像度の特徴マップに対しても適切に位置情報を考慮したマスク予測が行えます。

## トークン長とメモリ: コンテキスト長拡張と効率化

* **コンテキスト長の拡大**: Qwen2.5-VLはデフォルトで32kトークン程度まで拡張されています。本プロジェクトではモデルの`MODEL_MAX_LENGTH`を**最低でも16384**に設定し（Qwen2-VLのトレーニング上限に準拠）、長大なシーケンスにも対応できるようにします。視覚トークン数は画像1枚あたり最大～9k程度（2688pxの場合）となり、残りテキストトークンと合わせても16kを超えないように制御します。もし**1シーケンスに複数画像**を含める場合は、合計が16384を超えないよう各画像の解像度を下げる（例: 動画フレーム数を減らすように）動的制御が必要ですが、当面は1シーケンス1画像を前提とします。なお、Qwen2.5-VLは**mRoPEにより大きな位置IDにも対応**しており、長シーケンスでの性能劣化が少ないことが報告されています。

* **メモリと速度の最適化**: 解像度向上に伴う計算コスト増に対応するため、**高速なAttention実装**や**ウィンドウAttention**を活用します。本モデルはQwen2.5シリーズと同様にViT内にウィンドウAttentionを導入済みであり、画像分解能が高くなっても計算量を抑制できます。さらに、LLM部分の自己注意には最新のFlashAttention 2を有効化し、長いシーケンスでもメモリ効率と速度を改善します。具体的にはモデルロード時に`attn_implementation="flash_attention_2"`を指定し、学習・推論時に適用します（Qwen公式も推奨）。これらの最適化により、**高解像度画像でも現実的なバッチサイズで訓練可能**となります。

* **バッチあたりのトークン数監視**: 万一、バッチ内の全シーケンストークン総数（視覚＋テキスト）がモデルコンテキスト長を超過しそうな場合は、コレーターで**警告やスキップ**を行う仕組みを入れておきます。例えば、動的解像度実装後のデバッグ時に各バッチの最大シーケンス長をログ出力し、16384を超えるケースがないかチェックします。必要に応じてバッチサイズを自動で縮小するか、該当バッチの画像解像度を下げる処理を追加検討します（ただし通常はmax\_pixelsで制限しているため想定外の超過は起こらない見込みです）。

## 将来的な拡張と設計上の考慮

* **深度情報や3D拡張**: 今回の設計では深度情報の統合は行いませんが、**将来的に拡張しやすい構造**を意識します。Qwen2.5-VLは**時間軸を追加した3次元の位置埋め込み**（M-RoPE）に対応しており、画像を「2フレームの動画」として扱うことで時間次元を持たせています。この汎用的な枠組みを利用すれば、深度マップを追加チャネルや疑似フレームとして組み込むことも可能です。例えば、画像のRGBに対応するViT入力とは別に、同サイズの深度情報を第2フレームとして与え、ViTを3Dパッチ（空間×フレーム）で処理させることも考えられます。その際も現在の動的解像度実装（高さ・幅の可変、パッチグリッド管理）はそのまま応用できます。ただし**深度専用の位置エンコード**など追加設計が必要になるため、本段階では対応を盛り込まず、まず2D画像での土台を完成させます。

* **LISA改の基盤モデルとしての汎用性**: 最後に、本動的解像度対応によりLISA改は**入力画像の情報を余すところなく捉える**能力を獲得します。これは将来のFoodLMM改でセグメンテーションやカウントといったタスク特化のファインチューニングを行った際、高い上限性能を発揮できるポテンシャルとなります。今回導入する改良（高解像度画像対応、非正方形対応、長シーケンス対応）は、LISA改を単一タスク専用モデルにするものではなく、**汎用マルチモーダル基盤モデル**としての能力も維持します。Qwen2.5-VLの優れたドキュメント理解や物体カウント機能も引き続き活かせるよう、視覚エンコーダとLLM部分の接続（<|vision\_start|>/<|vision\_end|>トークンによる統合）はそのまま保ちます。一方で、マスクデコーダへの高精細特徴分岐は**追加ヘッド**として実装され、主タスク（対話や質問応答）を妨げません。これは、将来的にファインチューニングで**マルチタスク学習**（例：文章応答とマスク予測の両立）を行う余地も残しているということです。

以上のプランに従い実装を進めれば、最新のQwen2.5-VLの動的解像度機能とSAM2.1の高性能セグメンテーション機構を融合した「LISA改」モデルが実現できます。これにより、入力写真内の料理や食材の量を細部まで認識・推定できる基盤が整い、FoodLMM改での高度なドメイン適応に備えることができます。
